# Multi-app platform: fact verification

Checked by the fact-checker on 2026-09-24 against official sources only. No Octopus, Codefresh or Azure API was called.

**Verdicts:** CONFIRMED means an official source says so. REFUTED means an official source says otherwise. UNCLEAR means no official source settles it, so test it in the sandbox before relying on it.

**Sources.** `docs.octopus.com` returns a 301 redirect to `octopus.com/docs`, so the Octopus docs are cited there. Other sources:

- Official docs: `octopus.com/blog`, `codefresh.io/docs`, `learn.microsoft.com`, `kyverno.io` and `docs.sigstore.dev`.
- Vendor-owned GitHub repositories: `OctopusDeploy/Issues`, `OctopusDeploy/Calamari`, `OctopusDeploy/terraform-provider-octopusdeploy`, `sigstore/fulcio`, `kubernetes-sigs/azuredisk-csi-driver` and `codefresh-io/cli`.
- Lower weight: Octopus-maintained sample repositories under `OctopusSolutionsEngineering`.
- Supplementary, marked where used: `azure.microsoft.com` pricing pages, `octopus.com/downloads/whatsnew`, the Octopus pricing FAQ and Microsoft Q&A.

## 1. Octopus "Deploy a Release" step

| Question | Verdict | Exact behaviour and evidence | Source |
|---|---|---|---|
| Action type | CONFIRMED (not in the docs; from Octopus-maintained code) | `Octopus.DeployRelease`. It runs on the server (`Octopus.Action.RunOnServer = "true"`). Properties are `Octopus.Action.DeployRelease.ProjectId` and `Octopus.Action.DeployRelease.DeploymentCondition` (for example `IfNotCurrentVersion`). The child project is modelled as the step's primary package, from the built-in "Octopus Server Releases" feed: "packages can be project IDs when they are defined in a "Deploy a release" step". | [OctopusCopilot deploymentorchestration.tf](https://github.com/OctopusSolutionsEngineering/OctopusCopilot/blob/main/context/deploymentorchestration.tf), [OctopusTerraformExport converter](https://github.com/OctopusSolutionsEngineering/OctopusTerraformExport/blob/main/cmd/internal/converters/deployment_process_converter_base.go) |
| Identity and permissions of the child deployment | Child context CONFIRMED; creating user UNCLEAR | The child is an ordinary deployment of the child project, so it uses the child's own process, variables, accounts and lifecycle: "This deployment is no different from a deployment triggered directly." No official page says which Octopus user creates the child or which permission is checked. An official issue shows that a permission check does happen when the child is created: "Scheduled deployments will fail with a permission exception if they contain a deploy a release step" (fixed in 2019.1.5). | [Blog](https://octopus.com/blog/deploy-release-step), [Issue #5275](https://github.com/OctopusDeploy/Issues/issues/5275) |
| What the invoking user or team needs on the child project | UNCLEAR (undocumented) | The only evidence is issue #6369. A user without access to the child project who views the step gets "Missing permission: ProjectView". Test with the student role: ProjectView and ReleaseView on the child (needed to pick a child release) and DeploymentCreate on the child for that environment. | [Issue #6369](https://github.com/OctopusDeploy/Issues/issues/6369) |
| Child project in version control (config as code) | CONFIRMED | The official reproduction steps for a fixed bug use a Git parent: "Create some other other project (this can be either Git or Database project)". The docs also note that Git-stored processes reference "Projects on `Deploy a Release` steps" by slug. The step deploys a child *release*, which is a snapshot, so where the child's process is stored doesn't matter at deploy time. | [Issue #7628](https://github.com/OctopusDeploy/Issues/issues/7628), [Export/import](https://octopus.com/docs/projects/export-import) |
| Environment mapping | CONFIRMED: there is no mapping | The child is deployed to the environment and tenant of the parent's deployment. The chosen child release must be allowed there by the child's own lifecycle: "the release versions chosen for Project A and Project B must also be eligible to be deployed to the Test environment". Tenants: "the tenant will be used to trigger the child deployment", and an untenanted child ignores the tenant. Deployment conditions are Always, If not current, and If newer. A rolling step creates one child deployment per target. | [Deploy release step](https://octopus.com/docs/projects/coordinating-multiple-projects/deploy-release-step) |
| Does the parent wait, and fail if the child fails? | CONFIRMED (issue tracker; the docs page is silent) | The step waits for the child to finish, including its manual interventions. Issue #4500, where the step finished before the child's intervention was handled, was a bug fixed in 2018.6.13. The step's result follows the child's (#5898, #6658). Child interruptions are linked to the parent: "Used to handle interruptions in child deployments." No option to skip waiting is documented. Cancelling the parent doesn't cancel the child: "won't cancel the deployment of the child project". Retries and execution timeouts aren't available on this step. | [#4500](https://github.com/OctopusDeploy/Issues/issues/4500), [#5898](https://github.com/OctopusDeploy/Issues/issues/5898), [#6658](https://github.com/OctopusDeploy/Issues/issues/6658), [Interruptions API](https://octopus.com/docs/api/interruptions), [Step conditions](https://octopus.com/docs/projects/steps/conditions) |
| What flows from parent to child | CONFIRMED, in both directions | Parent to child: only the variables set on the step, and "Variables passed in will override existing variables in the child project if the names collide." Child to parent: "Any output variables generated by a deployment will be captured as output variables on the Deploy a Release step". They appear as `Octopus.Action[<step>].Output.Deployment[<child step>].<Name>`. No automatic sharing of the parent's secrets or accounts is documented. | [Deploy release step](https://octopus.com/docs/projects/coordinating-multiple-projects/deploy-release-step) |
| Licensing (context) | CONFIRMED | Orchestrator projects count toward the licence: "Octopus Deploy will count all active projects, regardless of whether they … are used to orchestrate the deployments of other Octopus Deploy projects." | [Pricing FAQ](https://octopus.com/pricing/faq) (supplementary) |

## 2. Octopus triggers for container images

| Question | Verdict | Exact behaviour and evidence | Source |
|---|---|---|---|
| External feed trigger: creates a release on a new image in an ACR feed? | CONFIRMED for images and Helm charts | "Any container images or Helm Charts referenced in your project's deployment process can be selected to trigger release creation." The trigger runs as a system task: "By default, triggers are evaluated every three minutes". The docs don't list feed types: "verified against most major Docker providers, compatibility is not guaranteed". An ACR feed is a Docker-registry feed type. | [External feed triggers](https://octopus.com/docs/projects/project-triggers/external-feed-triggers), [ACR feed](https://octopus.com/docs/packaging-applications/package-repositories/guides/container-registries/azure-container-services) |
| OCI artifacts that are neither images nor Helm charts | UNCLEAR | The docs cover only "container images or Helm Charts". A `FROM scratch` manifest image counts as an image. A non-image OCI artifact, such as one pushed with ORAS, is undocumented. | Same page |
| Built-in package repository trigger on ACR | REFUTED | "This trigger only supports the built-in package repository." It also allows only one channel per project and one trigger package, the one uploaded last. | [Built-in package repository triggers](https://octopus.com/docs/projects/project-triggers/built-in-package-repository-triggers) |
| Several images in one trigger | CONFIRMED (external feed triggers) | One trigger can watch several images. Terraform: "New versions of any of the packages you select will trigger release creation." The resulting release takes "all the latest container images or Helm Chart dependencies", not only the image that changed. A project can have several external feed triggers, for example one per channel. Advice for chains of images: trigger on the image "pushed to its repository last". | [Docs](https://octopus.com/docs/projects/project-triggers/external-feed-triggers), [TF `octopusdeploy_external_feed_create_release_trigger`](https://github.com/OctopusDeploy/terraform-provider-octopusdeploy/blob/main/docs/resources/external_feed_create_release_trigger.md) |
| How the release version is chosen | CONFIRMED | "The versions used for those releases is guided by release versioning under Settings." That setting is either a template (default `0.0.1`, counting up the patch number, with `Octopus.Version.*` and date variables) or "use the version number from" a package in a step (`DonorPackage`). Package versions come from the channel rules and use SemVer by default: "will not trigger off image tags such as `latest`". "Most recently published" ordering isn't supported for container or OCI registries. "Octopus will not create a release where the package has already been used". | [Release versioning](https://octopus.com/docs/releases/release-versioning), [Channels](https://octopus.com/docs/releases/channels), [Helm tutorial](https://octopus.com/docs/kubernetes/tutorials/automatically-track-third-party-helm-charts) |
| Projects stored in version control | CONFIRMED, with a limit | For config-as-code projects, "only container images and Helm Charts in the deployment process from the **default branch** are able to be referenced". The docs say nothing about built-in triggers with config as code, and built-in triggers can't read ACR anyway. | [External feed triggers](https://octopus.com/docs/projects/project-triggers/external-feed-triggers) |
| Cloud or plan limits | UNCLEAR: none documented | Neither the Octopus Cloud docs nor the pricing FAQ gates triggers. One related note: an ACR feed using OIDC (from 2025.2) "not supported for use with Kubernetes containers". The docs don't say whether a trigger can read an OIDC-authenticated ACR feed. | [Octopus Cloud](https://octopus.com/docs/octopus-cloud), [ACR feed](https://octopus.com/docs/packaging-applications/package-repositories/guides/container-registries/azure-container-services) |

## 5. Octopus secrets exposure

| Question | Verdict | Exact behaviour and evidence | Source |
|---|---|---|---|
| Are Git credential secrets exposed to deployment or runbook scripts? | UNCLEAR: not as variables, but they reach workers | No documented system variable exposes a Git credential, and Git dependencies are cloned on the server ("Server is the default and clones the repository"). The Argo CD steps and the Early Access "Commit to Git" step are different: both clone on the worker. For the Argo steps, Calamari receives the credential (password/PAT or SSH private key) in an encrypted custom-properties file (`ArgoCDCustomPropertiesDto.Credentials`). Commit to Git runs a user script next to the clone: "with the cloned destination repository available to it". Argo steps pick the credential by repository URL. In Commit to Git, whoever edits the process selects a credential from the library. | [API action templates](https://octopus.com/docs/api/action-templates), [Commit to Git](https://octopus.com/docs/deployments/git/commit-to-git), [Argo steps](https://octopus.com/docs/argo-cd/steps), [DTO](https://github.com/OctopusDeploy/Calamari/blob/main/source/Calamari.Contracts/ArgoCD/ArgoCDCustomPropertiesDto.cs) |
| Can any step in the project read a Sensitive variable (for example, a student printing it)? | CONFIRMED | "You can use these sensitive values in your deployment process just like normal variables". Scoping to environment or step narrows this, but an editor can change the scoped step. Log masking is best effort: "Note that this method isn't 100% foolproof." The docs warn to "consider who has permission to edit a project deployment or runbook process". For config-as-code projects, anyone who can push to a branch that releases are built from controls the process. Octopus "protected branches" "does not offer any protection outside of the Octopus UI". | [Sensitive variables](https://octopus.com/docs/projects/variables/sensitive-variables), [Converting](https://octopus.com/docs/projects/version-control/converting) |

## 6. Codefresh keyless signing identity

| Question | Verdict | Exact behaviour and evidence | Source |
|---|---|---|---|
| Issuer and audience | CONFIRMED | The issuer "is always https://oidc.codefresh.io". The audience defaults to `https://g.codefresh.io` on SaaS. "OIDC ID tokens expire after five minutes." `CF_OIDC_REQUEST_TOKEN` and `CF_OIDC_REQUEST_URL`: "Codefresh injects these two variables for every pipeline build". | [OIDC in pipelines](https://codefresh.io/docs/docs/integrations/oidc-pipelines/) |
| `sub` claim | CONFIRMED (manual format UNCLEAR) | Cron: `account:{accountId}:pipeline:{pipelineId}`. Git push: `account:{accountId}:pipeline:{pipelineId}:scm_repo_url:{url}:scm_user_name:{user}:scm_ref:{ref}`. PR: the same plus `:scm_pull_request_target_branch:{branch}`. Manual Git: `...:initiator:{user}:scm_repo_url:...`. The documented plain-manual form, `...:initiator{user}`, has no colon and its example omits `initiator`, so read a real token. Custom claims: `account_id`, `account_name`, `pipeline_id`, `pipeline_name` (`project/pipeline`), `workflow_id`, `initiator` and the `scm_*` claims. | Same |
| Does cosign/Fulcio accept the issuer? | CONFIRMED | Fulcio config: `https://oidc.codefresh.io`, `client-id: sigstore`, `type: ci-provider`. Certificate SAN: `{{.platform_url}}/{{.account_name}}/{{.pipeline_name}}:{{.account_id}}/{{.pipeline_id}}`, with a default platform URL of `https://g.codefresh.io`. Extensions: `build-signer-uri`/`run-invocation-uri` = `https://g.codefresh.io/build/<workflow_id>`, `build-config-uri` = `.../api/pipelines/<pipeline_id>`, and source repository URI and ref taken from the `scm_*` claims. Codefresh verifies its own images with `--certificate-oidc-issuer https://oidc.codefresh.io --certificate-identity-regexp "https://g.codefresh.io/codefresh-inc/.+:5672d8deb6724b6e359adf62/.+"`. The build step signs with `cosign: sign: true`. The docs.sigstore.dev page doesn't list Codefresh but notes "Fulcio also supports OIDC tokens from additional configured issuers." | [fulcio config.yaml](https://github.com/sigstore/fulcio/blob/main/config/identity/config.yaml), [Codefresh verify](https://codefresh.io/docs/docs/security/codefresh-signed-artifacts/), [Build step](https://codefresh.io/docs/docs/pipelines/steps/build/), [Sigstore](https://docs.sigstore.dev/certificate_authority/oidc-in-fulcio/) |
| Kyverno match for one pipeline | CONFIRMED (mechanism) | ClusterPolicy: `verifyImages[].attestors[].entries[].keyless {subject or subjectRegExp, issuer or issuerRegExp, rekor.url}`. ImageValidatingPolicy (`policies.kyverno.io/v1`, stable in Kyverno 1.19): `attestors[].cosign.keyless.identities[] {subject, issuer, subjectRegExp, issuerRegExp}` plus `ctlog.url`. For one pipeline, use issuer `https://oidc.codefresh.io` and a regex anchored on the immutable IDs, for example `^https://g\.codefresh\.io/<acct>/<project>/<pipeline>:<accountId>/<pipelineId>$`. The memo's `.../<app>/release:<id>/<id>` fits this if the Codefresh project is `<app>`. Kyverno's `additionalExtensions` fields are GitHub-specific, so the Codefresh ref extension can't be matched this way. | [verifyImages](https://kyverno.io/docs/policy-types/cluster-policy/verify-images/sigstore/), [IVP](https://kyverno.io/docs/policy-types/image-validating-policy/) |

## 9. AKS stop and start

| Question | Verdict | Exact behaviour and evidence | Source |
|---|---|---|---|
| Compute while stopped | CONFIRMED | Compute billing stops: "This action stops your control plane and agent nodes, allowing you to save on all the compute costs, while maintaining all objects except standalone pods." | [Start/stop](https://learn.microsoft.com/en-us/azure/aks/start-stop-cluster) |
| Control-plane fee while stopped | Free tier: no fee. Standard tier: UNCLEAR | The Free tier control plane is free anyway. The docs don't say whether the Standard per-cluster-hour fee applies while stopped. A Microsoft employee on Q&A (not docs) wrote: "Stopping an AKS cluster will not incur any additional costs". | [Pricing](https://azure.microsoft.com/en-us/pricing/details/kubernetes-service/) (supplementary), [Q&A](https://learn.microsoft.com/en-us/answers/questions/1234054/stopped-aks-cluster-on-standard-tier) |
| OS disks, load balancer and public IP while stopped | Managed disks, LB and static IP billed (CONFIRMED); ephemeral OS UNCLEAR | Deallocated VMs aren't billed, but "Some Azure resources, such as Disks and Networking continue to incur charges." Static IP: "charged for a static public IP address irrespective of the associated resource." Standard LB: billed per rule-hour, and "no hourly charge … when no rules are configured". The AKS load balancer keeps its rules (inference). AKS uses ephemeral OS disks when it can, and ephemeral OS disks don't support stop-deallocate, so how AKS stops such pools isn't documented. | [VM billing states](https://learn.microsoft.com/en-us/azure/virtual-machines/states-billing), [IP pricing](https://azure.microsoft.com/en-us/pricing/details/ip-addresses/), [LB pricing](https://azure.microsoft.com/en-us/pricing/details/load-balancer/), [Ephemeral OS](https://learn.microsoft.com/en-us/azure/virtual-machines/ephemeral-os-disks), [AKS storage](https://learn.microsoft.com/en-us/azure/aks/concepts-storage) |
| Maximum stopped duration | CONFIRMED | 12 months: "The cluster state of a stopped AKS cluster is preserved for up to 12 months." After that the state is deleted. Separately, a cluster with zero Ready nodes and no running VMs is stopped after 30 days. | [Start/stop](https://learn.microsoft.com/en-us/azure/aks/start-stop-cluster), [Support policies](https://learn.microsoft.com/en-us/azure/aks/support-policies) |
| Typical start time | UNCLEAR (not documented) | The docs give no duration. They say "wait 15-30 minutes before restarting your AKS cluster" after a stop, and warn that "customers may be unable to start a stopped cluster" in regions short of capacity. | [Start/stop](https://learn.microsoft.com/en-us/azure/aks/start-stop-cluster) |
| Restrictions | CONFIRMED | The cluster must be backed by Virtual Machine Scale Sets. It can't use Node Autoprovisioning (NAP). While stopped, only start and delete are allowed. Standalone pods are deleted. "The IP address of your API server may change." A private endpoint is recreated in the first node pool's subnet. Admission webhooks that match AKS-managed cluster-scoped resources, such as nodes, leases or clusterroles, can block the stop: "the stop operation may be rejected with a ValidationError. ## Design implications

1. **Deploy a Release into `platform-wake`.** Four consequences, plus one test:
   - The child's lifecycle must allow deployment to every environment at any time.
   - Each parent release snapshots a `platform-wake` release version.
   - The memo claim that "nothing reaches the parent" is wrong. The child's outputs flow back to the parent. A student can also pass variables that **override** `platform-wake` project variables. So `platform-wake` scripts and accounts must not read any project variable whose name a parent can guess; use constants in its process.
   - Test, as a student-role user, which identity and permissions child creation uses.
2. **Release creation.** App pipelines need no Octopus key if external feed triggers create releases. Trigger on the release manifest, which is pushed last. Use SemVer tags, because ACR can't order by publish date. Set release versioning from the manifest package. For config-as-code projects, the referenced images must be in the default branch.
3. **Argo CD pins.**
   - The image-tag step can't pin digests, and it deletes `digest:` from the `kustomization.yaml` `images[]` entries it updates. Keep tag pins plus locks plus Kyverno, or render digests with the Manifests step.
   - Annotations are the only binding, so only the platform should write Application manifests.
   - The integration is still Preview/Early Access. Re-test after every Cloud upgrade.
   - The Argo steps run on workers that receive Git credentials. Give them a platform-only worker pool.
4. **Scheduled runbooks.** Config-as-code runbook schedules run the default branch HEAD. Protect that branch in the Git provider; Octopus "protected branches" only guard the UI. Add channel Git protection rules for releases.
5. **Octopus secrets.** Anyone who can edit, or push, an app project's process can read its sensitive variables and can select library Git credentials in a Commit to Git step. Keep the Space Manager key and platform-repository write credentials out of any project or space that students can edit.
6. **Codefresh secrets.**
   - Turn off "Allow access to all users" on Git integrations and secret contexts.
   - Never import platform contexts into app pipelines.
   - Consider execution contexts.
   - Test whether an admin-started build can decrypt, and whether the clone step leaves the token in `.git/config`.
7. **Codefresh signing identity.** Any step in a pipeline can mint that pipeline's OIDC identity, so the release pipeline's YAML must be owned by the platform. In Kyverno, match issuer `https://oidc.codefresh.io` plus a SAN regex anchored on `:<accountId>/<pipelineId>$`.
8. **ACR.** Standard is enough for per-app tokens, up to 500. If app tokens hold `metadata/write`, apps can unlock their own tags. Lock tags with a platform identity instead of the app token.
9. **Cluster sleep.**
   - Stopped clusters still cost money: disks, LB rules and the static IP.
   - Exclude cluster-scoped resources from Kyverno's webhooks, or stops may be rejected.
   - Don't hard-code the API server IP.
   - Leave 15–30 minutes between stop and start.
   - The start is not guaranteed under capacity pressure.
   - After a start, check that disks have attached.
10. **Data disks in `rg-platform-<tier>-data`.**
    - Grant the control-plane identity Contributor, or the CSI permission set, on that resource group.
    - Use `reclaimPolicy: Retain`.
    - Clean up orphaned disks after cluster deletion.
    - Prefer ZRS, or make sure the node pool covers each disk's zone.
11. **SQL Server Express.** 2 GiB is the startup minimum, the buffer pool is capped at 1,410 MB, and SQL Server 2022 allows 10 GB per database. The memo's 2 GiB request, 2.5 GiB limit and `MSSQL_MEMORY_LIMIT_MB=2048` fit these limits.
12. **Federated credentials.**
    - Each identity allows at most 20 federated credentials, with no wildcards.
    - Keep at most 20 exact subjects per identity, for example one identity per app-environment.
    - Create them one at a time in Terraform (chained `depends_on`) to avoid 409 errors.
